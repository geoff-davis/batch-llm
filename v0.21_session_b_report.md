## 2. Harness architecture (Phase 4)

Package `benchmarks/scale_soak` (not shipped in the wheel or sdist):

```text
benchmarks/
    __init__.py
    README.md
    scale_soak/
        __init__.py     # public surface for tests
        __main__.py     # python -m benchmarks.scale_soak
        cli.py          # argparse CLI, profile resolution, per-scenario loop
        config.py       # profiles (ci/100k/1m/custom), ScenarioSettings
        fake_provider.py  # seeded FakeProviderStrategy + ScaleSoakClassifier
        monitor.py      # bounded resource sampling, WAL tracking, probes
        report.py       # RollingDigest, ScenarioResult, versioned report
        scenarios.py    # the eight scenario runners
```

Design points required by the plan and honored:

- Main scenarios drive the real `process_stream()` execution surface with a
  lazy async source and an aggregate-only sink; nothing materializes all
  items or retains one object per item.
- Per-item behavior derives from `sha256(seed:index)` — no behavior tables.
- All failures are injected exceptions classified by a harness
  `ErrorClassifier` through the production retry/cooldown paths; waits are
  milliseconds-scale.
- Each scenario runs in a fresh event loop so task/thread/fd baselines are
  honest.
- Exact item accounting uses an order-independent XOR-of-SHA-256 digest plus
  count and modular index-sum cross-checks (`RollingDigest`).

Scenarios (plan §8.1 A–H): `healthy`, `slow_consumer` (result high-water
must equal, never exceed, its bound), `rate_limit_wave` (provider calls
asserted exactly at `items + wave_size` — no retry storm), `transport_retry`
(physical retries exact against the seeded expectation),
`validation_recovery` (per-item `RetryState` feedback with in-provider
cross-item isolation assertions; failed-attempt tokens asserted retained),
`stop_resume` (category fail-fast, then `REUSE_SUCCESSES` restart with
replay-call elimination, current submission indexes, no duplicate rows, and
live-token exclusion asserted), `artifact_bench` (append/reopen/lookup/
iteration throughput, WAL plateau + close truncation, busy-checkpoint
recording, slow-reader concurrent-inspection subcase, JSONL comparison
capped at 20k records unless `--allow-large-jsonl`), and
`progress_overhead` (bundled renders bounded by elapsed refresh intervals,
not item count; a full-delivery user callback for comparison).

Report schema: `async-batch-llm-scale-soak` version 1 — UTC time,
environment (package version, git revision, Python, platform, CPU count,
resource-probe methods; no hostname/username/home paths), complete effective
configuration, counts/throughput/provider/queues/resources/artifact
sections, every assertion with evidence, caveats, and `deferred_features`
naming what v0.21 does not validate (#122 token-aware admission, #89
adaptive concurrency, distributed writers, provider-native batch APIs).
Unavailable metrics are `null`. Time series are bounded to 300 samples.

## 3. Invariant assertions

Enforced per scenario (plan §8.4 resource pass criteria):

- input/result queue high-water marks within configured bounds (and the
  slow-consumer bound is actually *reached*);
- expected vs observed digests equal in every scenario, both runs of
  stop/resume, and all three progress modes;
- replay eliminates provider calls exactly (`calls == items − replayed`);
- validation feedback observed only by its owning item;
- cooldowns started == cooldowns ended; provider calls exact through a 429
  wave;
- WAL plateau bounded by a page-size-derived limit during writes and during
  the slow-reader inspection subcase; WAL truncated (0 bytes) after clean
  close;
- named store executor threads terminate; tasks and fds return to baseline
  within configured tolerance (asyncio's lazily-spawned default-executor
  workers are counted and documented separately — `asyncio.run()` reclaims
  them at loop shutdown);
- optional `--max-post-warmup-rss-growth-mib` assertion; RSS is always
  reported.

  no prompt/output leakage into reports, and a reduced end-to-end CLI run.

Completed 2026-07-24T21:33:40Z on the same environment, exit code 0. Report:

| Scenario | Wall (s) | Items/s | Checks |
| --- | --- | --- | --- |

| stop_resume (both runs) | 604.1 | 1,655 | 12/12 |

Headline evidence:

- **Bounded memory at seven digits:** healthy's post-warm-up RSS growth over
  one million items was **−5.9 MiB** (peak process RSS 198 MiB) while the
  database grew to 1.5 GB on disk — the framework held its configured
  512/512 queue bounds exactly.
- **WAL plateau:** peak WAL 4.68 MB against a 1.5 GB database, 0 bytes after
  close.
- **Restart at scale:** stop_resume replayed every first-run success without
  a provider call and matched the full-source digest exactly.
- **Artifact backend at 1m:** 12,001 appends/s across 3,907 transactions,
  1,542 bytes/record, 4.4 ms reopen without history decode, 6,932 indexed
  lookups/s, 57,339 records/s bounded iteration, 6 ms close.

Same caveat as §7: fake-provider framework measurements on one machine.
Per the plan's dated-results policy, publishing these numbers in the docs
remains a maintainer decision; the docs currently link the harness and state
the policy without citing these runs.

## 10. Known limitations and deliberately deferred work

- The harness measures a fake provider: framework overhead only, never
  live-provider throughput, quotas, or cost.
- `progress_overhead`'s bundled mode drives the private `_ProgressReporter`
  with an injected non-terminal bar (recorded as a scenario caveat); the
  user-facing surface is `progress=True`.
- Scenario G reads private store telemetry (`_transaction_count`,
  `_page_size`, `_effective_wal_autocheckpoint_pages`,
  `_last_checkpoint_busy`) rather than expanding the public API — the
  Session A handoff's recommended trade-off.
- Token-aware admission (#122), adaptive concurrency (#89), distributed
  writers, and provider-native batch execution remain out of scope and are
  listed in every report's `deferred_features`.
