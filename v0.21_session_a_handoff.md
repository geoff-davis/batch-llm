## 3. Shared codec and JSONL parity

Private module `_internal/artifact_codec.py` now owns the common logical operations:

- canonical identity normalization and fingerprinting;
- prompt, context, and combined input fingerprinting;
- private `PreparedArtifactItem` state;
- manifest and terminal item-record construction;
- replay-key compatibility and replay restoration;
- stored-result decoding.

`JsonlArtifactStore` delegates those operations to the codec. Its logical schema remains
version 1 and its public behavior remains compatible.

New context-free records use a logical `None` context fingerprint. JSONL lookup retains a
private fallback to the v0.20 hash-of-`None` replay key, so an existing v0.20 artifact still
replays. A regression test covers that path.

JSONL `iter_results()` now:

- captures a finite byte-size high-water mark;
- reads bounded line pages on a worker thread;
- decodes and yields one result at a time;
- does not first materialize the complete record history or replay dictionary;
- excludes records appended beyond the captured snapshot;
- rejects malformed complete records while retaining the existing truncated-tail behavior.

`JsonlArtifactStore.read_results()` remains the explicit materializing convenience.

## 4. SQLite schema and versioning

Public implementation: `async_batch_llm.sqlite_artifacts.SqliteArtifactStore`.

Version markers:

```text
logical artifact schema: 1
SQLite physical schema: 1 (PRAGMA user_version)
application_id: 0x41424C21 ("ABL!")
```

Tables:

- `manifest`: one row with logical/physical versions, creation time, package version,
  initial canonical identity/fingerprint, and user metadata;
- `identities`: canonical identity JSON plus provider/model/version fields, keyed by
  `identity_fingerprint`;
- `item_records`: monotonic `record_sequence`, logical version, timestamp, item/submission
  identity, replay fingerprints, strategy class, success/error/replay eligibility, optional
  cost/raw inputs, and the serialized terminal result.

Indexes:

```text
idx_item_records_replay_all
  (identity_fingerprint, item_id, prompt_fingerprint, context_fingerprint,
   input_fingerprint, record_sequence DESC)
  WHERE replay_eligible = 1

idx_item_records_replay_success
  (identity_fingerprint, item_id, prompt_fingerprint, context_fingerprint,
   input_fingerprint, record_sequence DESC)
  WHERE replay_eligible = 1 AND success = 1

idx_item_records_success_sequence
  (record_sequence) WHERE success = 1
```

There is intentionally no uniqueness constraint on the replay key. Multiple attempts and
runs are retained, and `ORDER BY record_sequence DESC LIMIT 1` selects the newest compatible
terminal record.

Open validates the application ID, physical/logical versions, required tables, columns,
indexes, and manifest. Missing/zero-byte paths can be initialized. Directories, foreign
databases, malformed schemas, and future versions fail without replacement. `:memory:` and
SQLite URI filenames are rejected.

## 5. NULL replay semantics and query plans

The canonical predicate is exactly:

```sql
context_fingerprint IS ?
```

The binding is `None` for a context-free item and the canonical fingerprint string for an
item with context. The implementation contains no `context_fingerprint = ?` lookup.

The focused test writes one NULL and one non-NULL key, proves both replay without provider
calls, and runs `EXPLAIN QUERY PLAN` for both policies and both key shapes. SQLite selects:

- `idx_item_records_replay_success` for `REUSE_SUCCESSES`;
- `idx_item_records_replay_all` for `REUSE_ALL`.

The 100k acceptance database independently produced this NULL-key plan:

```text
SEARCH item_records USING INDEX idx_item_records_replay_success
(identity_fingerprint=? AND item_id=? AND prompt_fingerprint=?
 AND context_fingerprint=? AND input_fingerprint=?)
```

SQLite renders `IS ?` as `context_fingerprint=?` in the plan description; the executed SQL
and source assertion verify the NULL-safe predicate.

## 6. Durability and WAL lifecycle

`SqliteDurability.BALANCED` maps to WAL plus `synchronous=NORMAL`.

- `append()` resolves only after the transaction commits.
- A normal process crash should retain a consistent database and committed WAL history.
- A sudden OS/power failure may lose recently committed transactions since the last WAL
  synchronization/checkpoint. The loss window can contain more than one transaction.

`SqliteDurability.FULL` maps to WAL plus `synchronous=FULL`. It resolves after the fully
synchronized transaction commits and is the stronger, potentially slower power-loss mode.
Exact guarantees still depend on SQLite, the OS, filesystem, and storage hardware.

The private auto-checkpoint setting is explicitly 1,000 pages. The measured page size was
4,096 bytes. `close()` drains accepted writes, attempts `PRAGMA wal_checkpoint(TRUNCATE)`,
then closes the connection and terminates the owned executor. A busy checkpoint caused by an
external reader is recorded and does not imply data loss or loop forever. A non-busy
checkpoint/database error follows the retained-error policy.

The no-reader close tests and 100k acceptance run observed a zero-byte/removed WAL after
close. SQLite may leave an SHM sidecar after a healthy close; this is normal platform
behavior. A separate external-reader test covers the documented busy outcome, and a small
auto-checkpoint test verifies WAL growth is bounded.

## 7. Writer, cancellation, and retained errors

Each store owns:

- one `ThreadPoolExecutor(max_workers=1)`;
- one connection created, used, checkpointed, and closed on that thread;
- one async writer queue/task;
- one serialized stream of reads and writes through the owned executor.

`append()` serializes before queue ownership, enqueues without a cancellation point, and
awaits a per-request future. The writer collects up to `commit_batch_size`, waits at most
`commit_interval_seconds`, inserts within `BEGIN IMMEDIATE`, commits, and only then resolves
every append future. A batch failure rolls back and fails the active and queued owners.

Caller cancellation detaches only the wait. Accepted preparation, append, and close work
continues under store ownership. Detached failures are retained and raised exactly once by
the next observing public operation, including the first `close()`. Later close calls are
idempotent and silent unless cleanup creates a new error. Unexpected writer-task failure is
consumed and propagated rather than becoming an unobserved task exception.

An isolated Python 3.14.2 wheel smoke exposed a CPython executor-future completion race.
SQLite executor futures and owned lifecycle futures now use a cancellation-safe bridge with
a one-millisecond timer fallback. The final private-executor join is direct only after all DB
work has drained, avoiding creation of a default executor solely for shutdown. All SQLite
operations themselves remain on the owned thread.

## 8. Iterator snapshot and keyset behavior

SQLite `iter_results()` first flushes accepted writes, captures
`MAX(record_sequence)`, and pages using:

```text
record_sequence > last_sequence
record_sequence <= captured_high_water
ORDER BY record_sequence
LIMIT read_batch_size
```

Each page query fetches at most `read_batch_size` rows and returns from the executor before
the first row is decoded or yielded. Therefore no SQLite cursor or read transaction spans an
async yield or consumer await. Rows appended beyond the high-water mark are excluded from the
current iterator. `successes_only=True` uses the partial sequence index.

`SqliteArtifactStore.read_results()` is an async classmethod because SQLite I/O must remain
off the event loop; it returns a materialized `BatchResult`. This differs from the existing
synchronous JSONL convenience and should be called out in Phase 5 API documentation.

## 9. Queue diagnostics

`ProcessingStats` and its copied dictionary now include:

```text
input_queue_high_water_mark
result_queue_high_water_mark
```

Input tracking is performed synchronously at queue ownership: data items increment on
enqueue and decrement on dequeue. Finish sentinels are excluded. Result tracking increments
after a data result owns a result-capacity slot and is enqueued, then decrements before yield
or cleanup drain. End-of-stream and worker-crash control messages are excluded.

Both bounded and unbounded configurations report observed high-water values. Values start at
zero for a fresh processor, current data counts return to zero after a clean drain, and the
two high-water fields are included in the `batch_completed` observer payload.

## 11. Limitations, unresolved risks, and deviations

- This is a single-process store, not distributed work claiming, leasing, or cross-process
  exactly-once execution. Sequential reopen is supported; contention obeys the busy timeout.
- SQLite result inspection is bounded only through `iter_results()`. `read_results()` and
  `process_prompts()` intentionally materialize selected/all results.
- Large-run file size depends heavily on result metadata and payload shape. The local 100k
  number above must not be generalized.
- An SHM sidecar can remain after a successful close even when the WAL is truncated.
- The full suite ran on Python 3.12.12. Python 3.14.2 received an isolated built-wheel public
  import/write/reopen/replay smoke, not the full development suite.
- API docs, release notes, changelog, package version `0.21.0`, benchmark packaging, and CI or
  manual benchmark workflows are intentionally deferred to Session B/Phase 5. The built
  artifact therefore still has version `0.20.0`.
- No Phase 4 benchmark package or entry point was created, as required by the hard boundary.
- Plan drift was resolved without redesign: `ArtifactStore.iter_results()` already existed,
  and actual test filenames were used.
- The shared codec now represents context-free inputs as `None`; a legacy JSONL fallback was
  added so that this does not break v0.20 replay artifacts.

There are no unresolved test failures.
