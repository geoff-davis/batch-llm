## 2. Finding-by-finding resolution

### Path inspection used a writable store lifecycle

Resolved. `SqliteArtifactStore.read_results()` no longer constructs a store,
prepares a writable connection, records an identity, starts a writer, changes
WAL policy, or checkpoints. It owns a dedicated read-only connection and
reader thread for one materialization.

### Path inspection was not a bounded committed snapshot

Resolved. The reader captures the maximum committed record sequence once and
uses bounded keyset pages with `record_sequence > after` and
`record_sequence <= high_water`. Rows committed later are excluded from that
read and visible to a subsequent read.

### Cancellation could outlive reader resources

Resolved. SQLite work and connection ownership stay on one private executor
thread. Ordinary cancellation waits for the worker's `finally` block,
retrieves any worker exception, closes the connection, and joins the executor
before propagating `CancelledError`. If the caller cancels again during that
cleanup, shutdown becomes nonblocking; the worker still owns and closes its
connection, and its detached outcome is consumed without blocking the event
loop.

### An already-finished writer task could fail silently

Resolved. Writer completion is inspected both by its done callback and before
public operations, flush, and close. An exception, cancellation, or unexpected
clean exit becomes the store's persistent fatal error and fails active and
queued request owners.

### Detached operation errors could be lost

Resolved. An append/flush future whose caller was cancelled remains owned by
the store. Its eventual failure is retained until one public operation or
`close()` observes it.

### Operation and cleanup errors competed for one retained slot

Resolved. Fatal/detached operation failures and checkpoint/connection/executor
cleanup failures are tracked separately. Cleanup always finishes before
delivery. A distinct second error remains queued for the next `close()`.

### Repeated close behavior was ambiguous

Resolved. One owned close task performs cleanup exactly once and survives
caller cancellation. Store-level errors are delivered once in deterministic
order; repeated close is silent after the queue is exhausted.

### Post-review hardening

The approval review identified three narrow follow-ups, all now resolved:

- clean databases in writable directories use normal `mode=ro` locking and
  change detection, so a writer can safely start after inspection begins;
  `immutable=1` is limited to a clean database in a non-writable directory;
- repeated cancellation of `read_results()` cannot reach a synchronous
  `executor.shutdown(wait=True)` while the worker is still running;
- custom decoder failures identify whether the stored output or stored context
  decoder failed.

## 3. Identity, context, and compatibility semantics

Session A identity behavior remains unchanged. Without an explicit identity,
each prepared item's strategy identity is inferred and fingerprinted. The
first inferred canonical identity is pinned for that live store, and every
later item must match before lookup, append, or provider work. A new store may
pin a different homogeneous identity against the same artifact.

An explicit store-level `ArtifactIdentity` is still a caller-owned override for
a deliberately mixed run. In that mode, inferred per-item identities are not
compared. Identity mismatch errors do not include canonical identity JSON or
values from `ArtifactIdentity.extra`.

Inspection restores stored context only when `include_context=True` persisted
it. Missing, omitted, and stored-null context inspect as `None`; a configured
context decoder applies only to stored context. Replay never decodes or
substitutes historical context. It installs the current work item's context
and submission index.

No public class, method, parameter, return type, or import changed. No runtime
dependency was added. Both public artifact schema constants remain version 1:

```text
ARTIFACT_SCHEMA_VERSION = 1
SQLITE_SCHEMA_VERSION = 1
```

The physical SQLite schema, replay-key tuple, index definitions, NULL-safe
`context_fingerprint IS ?` lookup, JSONL v1 format, and SQLite schema-version-1
compatibility remain unchanged.

## 4. Read-only reader architecture

`SqliteArtifactStore.read_results()` now:

1. validates the path and page size without constructing a writable store;
2. creates one private, single-thread executor;
3. opens a filesystem URI with `mode=ro`, `uri=True`, autocommit, and
   `PRAGMA query_only=ON`;
4. uses normal SQLite locking and change detection in a writable directory,
   allowing a writer to start safely at any point during materialization
   (SQLite may create empty `-wal`/`-shm` coordination sidecars);
5. uses `immutable=1` only for a clean database in a non-writable directory,
   where the supported WAL writer lifecycle cannot start during the read;
6. validates the same application ID, schema versions, tables, columns,
   required index names, and manifest as the writable path;
7. captures one high-water sequence and decodes bounded keyset pages through
   the shared row validator and codec;
8. closes the connection on its owner thread and joins the executor after
   success, error, or ordinary cancellation; repeated cancellation requests
   nonblocking executor shutdown so the event loop never waits synchronously.

The instance method `store.iter_results()` intentionally keeps its existing
live-store contract: it settles store errors, prepares, flushes accepted
writes, and then iterates its own finite high-water snapshot.

## 5. Close error state machine

The fatal error remains persistent store state even after its first delivery.
Observation only suppresses duplicate delivery; it never makes the store
usable again. The close task completes checkpoint, connection close, and
executor shutdown before adding errors to the delivery queue.

| Situation | First completed `close()` | Second `close()` | Later closes |
| --- | --- | --- | --- |
| No errors | returns | returns | return |
| Unobserved writer/detached error only | raises operation error | returns | return |
| Cleanup error only | raises cleanup error | returns | return |
| Distinct operation and cleanup errors | raises operation error | raises cleanup error | return |
| Operation error already observed, then cleanup fails | raises cleanup error | returns | return |
| Caller cancels close | caller gets `CancelledError`; owned cleanup continues | delivers queued errors in the rows above | return after queue drains |

Preparation errors follow the same observed/unobserved rule. Executor shutdown
is guarded and performed once.

## 7. Regression coverage

SQLite reader tests now cover:

- `mode=ro` URI use and absence of schema, identity, journal-policy, checkpoint,
  insert, and create statements;
- no writable prepare/writer lifecycle;
- repeated clean reads with unchanged database mtime;
- database mode `0444` in a directory mode `0555`;
- a writer starting after a clean reader opens, with finite-snapshot behavior;
- a finite active-writer snapshot, later visibility, writer progress, and no
  reader checkpoint/WAL truncation;
- ordinary and repeated cancellation with connection and reader-thread cleanup;
- `successes_only`, missing paths, text/empty databases, future schemas, and
  strict logical row-version validation.

Lifecycle tests now cover:

- an idle already-crashed writer;
- writer plus cleanup failures delivered over two closes;
- detached append plus cleanup failures delivered over two closes;
- an already-observed writer failure followed by cleanup failure;
- a connection-close failure delivered once;
- cancelled close retaining cleanup errors;
- executor shutdown exactly once and silent later closes.

The initial focused regressions produced five expected failures before
implementation: writable path inspection, writable lifecycle use, hidden idle
writer crash, writer/cleanup ordering, and detached/cleanup error loss. Those
same regressions passed after implementation.
