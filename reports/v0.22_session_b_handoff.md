`TokenEstimate` rejects booleans, non-integers, and negative input/output


TPM accepts only a positive integer or `None`. RPM now rejects booleans and
non-finite values while retaining positive integer/float and sub-one behavior.

`LLMCallStrategy` has this default hook:

```python
def estimate_tokens(
    self,
    prompt: str,
    attempt: int,
    state: RetryState | None,

    return None
```

`CallableStrategy` and `ModelStrategy` accept `token_estimator=` conveniences.
Resolution precedence is the processor estimator, then the effective
strategy's hook, then a framework-owned failure.

The public framework errors and stable categories are:

## 4. Gate algorithm and clock design

Each quota-scope entry still owns exactly one `QuotaGate`. That gate now
atomically evaluates both configured dimensions at the FIFO head:

- request refill is `max_requests_per_minute / 60` per second;
- request capacity is `max(1.0, max_requests_per_minute)`;
- token refill is `max_tokens_per_minute / 60` per second;
- token capacity is `max_tokens_per_minute`;
- both buckets start full;
- an admission consumes both dimensions in one synchronous mutation;
- RPM-only, TPM-only, combined, and fully disabled modes share the same gate;
- an estimate larger than token capacity fails immediately;
- a small arrival cannot bypass an older large waiter;
- refunds, reconciliation, refill, cancellation, and shutdown reconsider the
  FIFO head;
- immediate admission creates no waiter and no wake task;
- at most one refill wake task is owned per gate;
- disabled admission invokes no estimator and allocates no waiter/timer.

Production uses `time.perf_counter()` and `asyncio.sleep()`. Private injected
clock and sleep hooks drive deterministic unit tests without a public clock
configuration or global monkeypatch. Floating-point bucket comparisons use a
small tolerance. Token demand and observed usage remain integer quantities.

The gate is an event-loop-owned in-process primitive. Reservation, refund, and
reconciliation mutations contain no await point and make no thread-safety
claim.

## 5. Exact reservation state machine

The centrally owned lifecycle is:

```text
waiting -> reserved -> provider_started -> finalized
                    \-> finalized_before_start
```

The operations are:

1. `reserve()` grants request and token capacity atomically.
2. `mark_provider_started()` fixes the billing-risk boundary immediately
   before provider coroutine scheduling.
3. `finalize_before_start()` refunds both configured dimensions.
4. `reconcile(actual)` consumes the request reservation and adjusts token
   capacity to known actual usage.
5. `finalize_unknown()` consumes the request reservation and retains the token
   estimate after provider start.
6. `finalize_request_only()` retains Session A RPM-only behavior.
7. Any second finalization observes the stored result and cannot mutate the
   gate again.

The completed reconciliation table is:

| Outcome | Request | Tokens |
| --- | --- | --- |
| Replay, middleware skip, dry run | None | None |
| Estimator or preparation failure | None | None |
| Cancel/deadline/abort while waiting | None | None |
| Cancel/deadline/abort after reservation but before provider start | Refunded | Refunded |
| Capacity cancellation before provider start | Refunded | Refunded |
| Provider success with known usage | Consumed | Reconciled to actual |
| Provider failure with known usage | Consumed | Reconciled to actual |
| Explicit known zero | Consumed | Fully refunded |
| Provider failure with unknown usage | Consumed | Estimate retained |
| Timeout or external cancellation after provider start | Consumed | Estimate retained |
| Unknown rate-limit failure | Consumed | Estimate retained |
| Invalid provider return with no recoverable usage | Consumed | Estimate retained |

If actual usage is lower, the unused reservation is refunded and capacity is
capped at burst maximum. If actual usage is higher, the difference is charged
immediately and token availability may become negative. That debt is not
clamped or discarded; future admission waits for refill to repay it.

## 6. Known and unknown usage rules

For successful strategy mappings:

1. A valid explicit `total_tokens` wins.
2. Otherwise explicit input/output fields are summed.
3. Cached-input tokens remain available to normal accounting but are not
   automatically subtracted from TPM.
4. A mapping with recognized explicit zero values is known zero.
5. An empty or unrecognized mapping is unknown.
6. Invalid values follow the existing invalid-return/error path and cannot
   cause a false refund.

For failures, explicit `_failed_token_usage` and successfully coerced provider
usage objects are known, including zero. Missing or malformed usage is unknown
with non-negative zero display values. Best-effort extraction cannot replace
the provider error, and `CancelledError` still propagates.

The existing `TokenExtractor.extract_from_exception()` dictionary shape and
`ParallelBatchProcessor._extract_token_usage()` override point remain intact.
A non-zero custom override is treated as known. An all-zero override without an
explicit provider signal remains conservatively unknown; custom subclasses can
stamp `_failed_token_usage` to communicate exact zero.

Known provider usage is reconciled before application `after_process`
middleware. If later framework/application work fails, normalized usage is
stamped onto that failure so existing failed-attempt billed-token accounting
remains exact.

## 7. Physical-attempt order and retry semantics

Every physical live try uses this shared order:

1. Check item/batch deadline and abort state.
2. Run `before_process` middleware.
3. Return a filtered result without live admission when middleware skips.
4. Resolve and prepare the effective middleware-replaced strategy.
5. Resolve that strategy's classifier, quota scope, estimator, and capacity
   ownership.
6. Bypass cooldown, estimator, quota, and provider capacity for dry run.
7. Wait for the effective scope's coordinated cooldown.
8. Apply the scope's post-cooldown slow-start delay.
9. Resolve and validate the estimate when TPM is enabled.
10. Atomically reserve RPM and TPM at the FIFO head.
11. Acquire independent provider capacity.
12. Mark provider start and invoke `strategy.execute()` under guardrails.
13. Normalize usage and reconcile before application postprocessing.
14. Release provider capacity and continue existing result, retry, checkpoint,
    observer, accounting, and publication behavior.

No provider capacity is held during estimation or quota waits. No quota
reservation is held during cooldown. Attempt timeout still surrounds provider
execution only, while item/batch deadlines include cooldown, estimation, quota,
and capacity waits.

Every physical retry estimates and reserves again. Rate-limit retries retain
their logical attempt number but receive a new physical try number and
reservation. Transport, validation, and escalation retries advance the logical
attempt according to existing semantics.

Artifact replay remains outside the live executor. Replay, dry-run, middleware
filter, and preparation-failure paths invoke no estimator and consume or mutate
no live cooldown, RPM, TPM, or provider-capacity state.

## 8. Timing, statistics, events, and metrics

The following fields are appended to `AttemptTiming` after every v0.21 field:

```text
quota_wait_seconds
estimated_input_tokens
estimated_output_tokens
reserved_tokens
reported_tokens
reconciliation_delta_tokens
quota_scope_id
```

`reported_tokens=None` means unknown and `reported_tokens=0` means known zero.
The reconciliation delta is `actual - reserved`. `quota_scope_id` is a
run-local ordinal, not a stable identity. `WorkItemTiming` and `WorkItemResult`
expose aggregate `quota_wait_seconds` without changing provider-capacity
`admission_wait_seconds`.

`ProcessingStats` adds current-run-only totals for quota wait, estimate split,
reservations, known reported reconciliation, refunds, underestimation debt,
unknown attempts, known-zero attempts, estimation failures, admitted attempts,
and scope count. Quota wait samples use the existing bounded 10,000-sample
policy and expose p50/p95/p99. Estimated/reserved amounts remain separate from
actual billed-token totals. Replay and dry run do not enter live quota totals.

`BatchResult.summary()` stays quiet when quota admission was not observed. When
active, it shows quota-wait percentiles and a concise reservation,
reported-token, refund, debt, and unknown line without presenting estimates as
billed usage.

The additive events are:

- `QUOTA_ADMITTED`, once per granted live reservation;
- `QUOTA_RECONCILED`, once per started reservation finalized with known or
  unknown usage.

Payloads contain safe item/worker/attempt/try data, run-local scope ordinal,
configured dimensions, wait cause, estimate split, reservation, reported
total, known flag, delta, and disposition. They contain no prompt, scope object,
credential, raw response, or raw provider error.

`MetricsObserver` aggregates quota admission/wait, estimates, reservations,
known reconciliation, refunds, debt, unknown/zero attempts, estimation
failures, and observed scope count in dictionary, JSON, and Prometheus output.
No item ID or raw scope value becomes a metric label.

## 12. Risk review

The final review explicitly covered the five requested risk areas.

### Reconciliation

- Gate accounting mutates only through `QuotaReservation`.
- Finalization state is set before the synchronous gate mutation and cannot be
  applied twice.
- Refunds are capped at burst capacity.
- Underestimation creates negative debt and wakes/re-evaluates waiters without
  discarding the debt.
- Known usage is reconciled before later middleware can obscure it.
- Every physical retry owns an independent reservation.

No blocking reconciliation finding remains.

### Cancellation races

- A cancelled ungranted FIFO waiter is removed and the next waiter is checked.
- Shielding makes an already-granted reservation observable; both the gate and
  outer guardrail cleanup safely finalize an unseen grant exactly once.
- Cancellation during capacity wait refunds request and token dimensions.
- The provider-start callback is synchronous and immediately precedes provider
  coroutine scheduling.
- Cancellation after that callback conservatively retains unknown token demand.
- Gate cleanup contains no await point; repeated cancellation cannot split a
  refund/reconciliation mutation.
- Registry shutdown wakes every waiter and attempts every scope cleanup even if
  another cleanup fails.

No blocking cancellation-race finding remains.

### Timing

- Quota wait is distinct from cooldown, provider-capacity admission, execution,
  provider time, and retry backoff.
- Attempt timeout starts around provider execution, not estimation or quota.
- Item/batch deadlines include every pre-provider wait and remove waiters
  without a late provider call.
- Samples are bounded and default summaries remain quiet when disabled.

No blocking timing finding remains.

### Serialization and privacy

- Schema v1 is retained with additive optional/defaulted fields.
- `None` and zero usage remain distinct through JSON/JSONL round trips.
- Scope ordinals are serialized; arbitrary scope values are not.
- Estimator failures redact raw causes, and no prompt/callable identity is added
  to diagnostics.

No blocking serialization/privacy finding remains.

### Compatibility

- v0.21 positional `AttemptTiming` construction and shaped records are tested.
- Actual token accounting and artifact identity retain their prior meanings.
- RPM-only and fully disabled paths retain Session A behavior.
- All execution surfaces use the shared executor path.
- Replay, dry run, filtering, preparation failure, and cleanup boundaries are
  preserved.

No blocking compatibility finding remains.

## 13. Performance observations and known limitations

Observed implementation properties:

- TPM-disabled execution performs no estimation.
- A disabled gate allocates no waiter or timer; an immediate enabled admission
  also creates no refill wake task.
- Wait-state memory is proportional to live waiters and registered scope/
  strategy identities, not completed item count.
- Quota percentile storage is capped at 10,000 samples.
- Synchronous estimators run through the default executor so they do not block
  the event loop; asynchronous estimators run directly under guardrails.
- The full CI suite remains green, but Session B deliberately adds no new
  100,000-item performance evidence. That is Session C work.

Known limitations:

- The bucket is a local in-process smoother, not cross-process coordination and
  not an exact emulation of every provider fixed/rolling window.
- Strict FIFO can cause head-of-line blocking when a large estimate precedes
  smaller work.
- Unknown started usage retains the estimate. This can temporarily underuse a
  quota after a truly unbilled failure, but avoids optimistic refund storms.
- Python cannot forcibly stop a synchronous estimator already running in a
  worker thread. Deadline/cancellation stops the framework wait and prevents a
  provider call, but the local estimator function may finish in the background.
  Estimators should therefore be finite, local, and side-effect-free.
- A custom processor override returning all-zero usage without an explicit
  provider signal is conservatively unknown. Stamp `_failed_token_usage` for
  exact zero.
- v0.22 enforces one combined token budget; separate input/output budgets and
  weighted fair scheduling are intentionally deferred.
- The character estimator is approximate and explicit; callers needing model
  accuracy must provide an appropriate local tokenizer.
- Scope identities are retained strongly until host cleanup, bounded by unique
  live registered identities.

## 14. Exact Session C scale assertions

The Session C token-aware scenario should assert and record all of the
following without changing Session B semantics.

### Terminal and attempt integrity

- submitted, accepted, terminal, succeeded, failed, skipped, replayed, and
  aborted item counts;
- exact unique terminal item IDs, with missing and duplicate counts equal to
  zero;
- logical attempts, physical tries, provider-start callbacks, and provider
  invocation count;
- one `QUOTA_ADMITTED` per granted live physical attempt;
- one `QUOTA_RECONCILED` per provider-started physical attempt;
- no provider invocation for replay, dry run, filter skip, estimator failure,

### Token conservation

- estimated input/output and total reserved tokens;
- known reported reconciliation tokens;
- overestimate refunds, pre-start refunds, and underestimation debt;
- known-zero and unknown started-attempt counts;
- the identity `net token charge = reserved - refunded + underestimated`;
- for known started attempts, reported actual equals reserved minus
  overestimate refunds plus underestimation debt;
- fake-provider billed token totals remain separate from all estimates and
  match the scenario's deterministic expected actual totals;
- every retry scenario contributes a fresh reservation and finalization.

### Admission behavior

- total, maximum, p50, p95, and p99 quota wait, with non-zero measurable wait;
- provider-capacity `admission_wait_seconds` measured separately;
- no provider-capacity occupancy while a task is estimating or waiting for
  quota;
- no quota reservation held while a scope is in coordinated cooldown;
- shared scopes consume one RPM/TPM budget while distinct scopes progress
  independently;
- strict FIFO ordering, including an intentionally mixed-size head-of-line
  case;
- debt delays subsequent admissions until refill repays it.

### Boundedness, cleanup, and privacy

- quota samples never exceed 10,000 and metric scope state never exceeds the
  number of registered run-local scopes;
- peak/final RSS, event-loop lag, wall time, throughput, and memory growth;
- gate waiter count is zero, no refill wake task remains, and no worker,
  producer, stream, cooldown, or result-handoff task leaks after cleanup;
- artifact replay adds no current-run reservation/reconciliation totals;
- reports contain no prompt, output, credential, raw scope representation,
  raw exception, or unstable estimator representation;
- JSON/JSONL artifacts remain readable and preserve optional quota timing.

The harness should report these values by scenario and quota-scope ordinal
where useful, without adding item IDs as metric labels. Workload totals and
limits should produce real but short waits rather than minute-long test runs.

## 15. Session C risks and stop boundary

Session C should begin from the reviewed Session B implementation SHA above and
must preserve the locked semantics rather than tune them to make a benchmark
pass. Particular risks are:

1. Treating estimator worker-thread completion after caller cancellation as a
   leaked provider task. The harness must distinguish local estimator cleanup
   from provider-start accounting.
2. Measuring configured estimates as billed usage instead of reporting the two
   quantities independently.
3. Hiding underestimation debt through refill or aggregate rounding.
4. Letting observer/reporting overhead dominate the token scenario.
5. Masking FIFO head-of-line behavior by using uniform estimates only.
6. Accidentally sharing or separating budgets through equal rather than
   identical scope objects.
7. Counting replayed historical timing as current-run quota consumption.
8. Adding unbounded per-item samples or high-cardinality labels to obtain scale
   evidence.
9. Changing release documentation, package version, changelog, or GitHub state
   before the Session B review gate is satisfied.

Stop at this handoff. Do not begin Session C in this implementation or review
diff.
