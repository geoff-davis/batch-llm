## 3. Scale scenario design

`token_quota_mixed` uses a generated item stream and consumes
`process_stream()` results incrementally. It retains bounded samples,
aggregates, a rolling order-independent digest, and per-band maxima rather than
all `WorkItemResult` objects.

For 100,000 items, the deterministic mix is:

| Band | Items | Estimated input/output/total | Actual input/output/total |
| --- | ---: | ---: | ---: |
| Small | 94,000 | 4 / 4 / 8 | 3 / 2 / 5 |
| Medium | 5,000 | 30 / 20 / 50 | 30 / 20 / 50 |
| Large | 1,000 | 3,000 / 1,500 / 4,500 | 3,200 / 1,800 / 5,000 |

The small band refunds three tokens per ordinary attempt. The medium band is
exact. The large band creates 500 tokens of debt per attempt. Three selected
items add the remaining semantics without changing distribution size:

- one validation failure reports 25 input and 15 output tokens, then succeeds
  on a fresh reservation;
- one transport failure has unknown usage, retains its first reservation, and
  then succeeds on a fresh reservation;
- one success reports explicit known-zero usage and refunds its full estimate.

Items route between two effective strategies after middleware resolution. The
strategies have distinct quota-scope objects and share one concurrency-scope
object. Each scope owns the same independent RPM/TPM settings. The fake
provider tracks calls, physical attempts, usage, bands, concurrency, and
retries independently of the quota-gate implementation. It uses no network or
credentials.

The scenario uses the public 60-second quota semantics. There is no benchmark
window override. Reduced runs size the initial bucket from total per-scope
work. Runs of at least 10,000 items size it from the initial large-band burst,
leaving a modest refill tail. RPM is configured high enough that the scenario
specifically exercises TPM while still using the atomic combined gate.

The scenario asserts exact terminal accounting, digest equality, every band,
physical calls, retries, usage totals, refund/debt totals, known-zero versus
unknown behavior, measurable quota waiting, scope balance, FIFO timing
summaries, queue bounds, provider concurrency, absence of overload storms,
bounded memory, and task/thread/FD/store/scope cleanup.

## 4. Scale report schema

The scale-soak report schema is now:

```text
schema_name: async-batch-llm-scale-soak
schema_version: 2
```

Each scenario record appends a `quota` object. For the mixed-token scenario it
contains:

- band counts, per-band estimates, actuals, fairness, and maximum waits;
- the deterministic expected oracle;
- observations derived independently from attempt timings, result usage,
  batch stats, and observer events;
- estimated input/output, reserved, reported/reconciled, refunded, and debt
  totals;
- known-zero and unknown attempt counts;
- total/max/p50/p95/p99 quota waits;
- admitted/reconciled event counts, dispositions, and ordinal scope counts;
- post-cleanup admission registry and background-task state.

Schema 2 deliberately removes token-aware admission from the scale report's
deferred-feature list. The application result/artifact schema remains version
1 with additive defaulting fields, as required for v0.21 compatibility. These
are separate schemas.

The report environment excludes hostname, username, home path, prompt, output,
and raw quota-scope representations. Scope identity is reported only as a
bounded ordinal. The report test suite rejects raw prompt/output leakage.

## 11. Risk review

### Reconciliation and exactly-once accounting

The deterministic oracle cross-checks estimates, physical reservations,
reported usage, refunds, debt, known zero, unknown usage, retries, attempt
timings, batch stats, and both quota event types. The 100k totals agree across
all sources. Dedicated fake-clock tests cover exact/debt/refund/unknown and
idempotent finalization. No blocking finding remains.

### Cancellation and provider-start races

Focused tests cover cancellation, item deadline, batch deadline, abort, and
capacity cancellation while queued; pre-start paths refund both dimensions.
Post-start timeout/cancellation retains the estimate unless known usage was
recovered. Provider capacity is acquired only after quota and the synchronous
provider-start boundary remains the billing-risk boundary. Cleanup tests show
no waiter, wake task, scope entry, worker, or stream-task leaks. No blocking
finding remains.

### Timing and bounded observability

Quota estimation/wait/reconciliation fields remain separate from provider
capacity and `admission_wait_seconds`. Percentile samples are capped at 10,000
and scale reporting uses bounded per-band aggregates. The 100k report's zero
p50/p95/p99 with a non-zero maximum is expected because fewer than one percent
of attempts waited. Event data uses bounded scope ordinals and metrics create
no item-ID labels. No blocking finding remains.

### Serialization and privacy

Application result schema version 1 round-trips `reported_tokens=None` versus
known zero and defaults v0.21 records safely. Scale report schema 2 includes no
prompts, outputs, arbitrary scope representations, usernames, hostnames, or
home paths. Failure serialization remains redacted. No blocking finding
remains.

### Compatibility and bypass behavior

v0.21-shaped result JSON restores quota fields with safe defaults. Existing
JSONL and SQLite artifacts replay without checkpoint invalidation. Replay does
not invoke the estimator, gate, cooldown, provider capacity, or provider, and
changed local RPM/TPM configuration does not alter artifact identity. Dry run,
middleware filtering, and preparation failure remain admission-neutral. Batch,
stream, single-call, gateway, and `LLMCallPool` share the same executor path.
No blocking finding remains.

The old v0.21 wheel was not used to read v0.22 records, and no backward-reader
claim is made.

## 13. Explicit limitations and unsupported claims

- Quotas are event-loop-owned, local, in-process rolling smoothers. They are
  not distributed coordination and may not reproduce provider window details.
- FIFO provides deterministic fairness but can expose head-of-line blocking
  when a large estimate leads the queue.
- A synchronous estimator is dispatched off-loop; cancellation stops the
  framework wait but cannot forcibly terminate an already running thread.
- Unknown post-start usage retains the estimate by design and may be
  conservative.
- Gateway-hidden attempts and billing cannot be reconciled unless exposed
  upstream.
- TPM does not schedule active GPU sequences, KV-cache, or instantaneous active
  tokens.
- Character-based estimation is approximate and is never enabled implicitly.
- Scale evidence uses a deterministic fake provider and is not a live-provider
  throughput, pricing, or quota-equivalence claim.
- Only the `healthy` scenario has post-refactor one-million-item evidence.
- The raw benchmark JSON reports are gitignored local evidence. Their hashes and
  dated summaries are tracked, but reviewers need the files transferred or the
  commands rerun to inspect every machine-readable field.
- Adaptive concurrency remains deferred to a later release.
